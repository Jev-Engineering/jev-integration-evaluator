# Objective

Create a complete reusable agent skill that analyzes arbitrary software codebases to identify, evaluate, prioritize, design, and validate **ideal locations for integrating JEV / TypeSafe AI**.

The skill must go substantially beyond searching for obvious keywords. It should understand code structure, control flow, agent loops, tool routing, retrieval pipelines, retry logic, graph mutation, validation logic, risk boundaries, and other architectural decision points, then determine:

1. **Where JEV should be inserted.**
2. **Why JEV is appropriate at that location.**
3. **Where JEV should explicitly NOT be used.**
4. **What JEV primitive/pattern should be used.**
5. **What questions/choices JEV should evaluate.**
6. **What surrounding logic should remain deterministic.**
7. **When JEV should run.**
8. **When it should be bypassed.**
9. **What confidence thresholds and fallback behavior should be used.**
10. **How the proposed integration should be experimentally validated.**
11. **Whether the benefit of JEV outweighs its latency, cost, complexity, and failure risk.**
12. **Which candidate integrations should be implemented first.**

The skill should work across:

- ordinary applications,
- AI agents,
- coding agents,
- autonomous agents,
- RAG systems,
- GraphRAG systems,
- multi-agent systems,
- workflow engines,
- API services,
- CLI applications,
- data pipelines,
- games and game-playing agents,
- robotics/control systems,
- code-review systems,
- security systems,
- orchestration systems,
- graph/database systems,
- long-running autonomous systems.

The resulting skill must support both:

- **analysis-only mode**, producing recommendations, and
- **implementation mode**, where an authorized agent can modify the codebase, add JEV integration, tests, instrumentation, and benchmarks.

Do not build a generic "add JEV everywhere" tool. The central purpose is to discover **high-leverage, semantically appropriate insertion points** while avoiding unnecessary or harmful JEV usage.

---

# Core principle

The skill should operationalize this concept:

> JEV is most useful at semantic decision boundaries where messy or ambiguous information must be reduced to a bounded set of structured choices, particularly when the downstream consequence of making the wrong decision is significant.

Use the following conceptual placement heuristic:

```text
JEV Placement Value
    ∝
Semantic Uncertainty
× Downstream Consequence
× Decision Boundedness
× Decision Frequency
× Recoverability Value
```

But this should not remain conceptual.

Implement an explicit scoring model.

---

# 1. Create a JEV Placement Score

For every candidate insertion point, calculate a structured score.

At minimum evaluate:

```text
semantic_uncertainty
decision_boundedness
downstream_consequence
decision_frequency
cost_of_wrong_decision
recoverability_value
observability
deterministic_alternative_quality
current_failure_rate
current_llm_dependency
latency_sensitivity
cost_sensitivity
implementation_complexity
testability
expected_reuse
confidence_calibration_value
```

Use normalized values such as:

```text
0.0 – 1.0
```

Create an overall score such as:

```text
placement_score =
    + semantic_uncertainty
    + decision_boundedness
    + downstream_consequence
    + cost_of_wrong_decision
    + recoverability_value
    + current_llm_dependency
    + testability
    + expected_reuse
    - deterministic_alternative_quality
    - latency_sensitivity
    - implementation_complexity
```

Do not blindly use equal weights.

Provide documented default weights and allow configuration.

The skill must output both:

- the composite score,
- every underlying dimension.

Never hide the reasoning behind only one aggregate score.

# 3. Explicitly recognize the strongest JEV insertion patterns

The skill should contain first-class detectors and playbooks for the following patterns.

## Pattern A — Before tool execution

Example architecture:

```text
LLM reasoning
    ↓
candidate actions
    ↓
JEV
    ↓
typed action
    ↓
deterministic executor
```

Potential JEV decisions:

```text
search
inspect
edit
test
commit
escalate
stop
```

Evaluate whether JEV can improve:

- tool selection,
- argument selection,
- confidence,
- avoidance of unnecessary tool calls,
- dangerous-action prevention.

---

## Pattern B — Before irreversible or expensive actions

Detect actions such as:

```text
delete
merge
push
deploy
publish
send
purchase
restart
modify permissions
modify production data
drop database objects
overwrite files
perform migrations
execute privileged commands
```

Recommend JEV as an assessment layer when semantic interpretation matters.

Architecture:

```text
proposed action
     ↓
    JEV
     ↓
risk / confidence / approval requirement
     ↓
deterministic policy
     ↓
execute / inspect / request approval / block
```

Important:

**JEV evaluates. Deterministic code owns final policy.**

Do not allow JEV to become the sole security boundary for actions that can be checked deterministically.

---

## Pattern C — Tool/function routing

Detect dispatchers such as:

```text
tool_router
dispatcher
function_calling
command_router
action_registry
workflow_router
```

Determine whether free-form LLM routing can be replaced or supplemented with bounded JEV choices.

---

## Pattern D — Retrieval → generation boundary

Detect:

```text
query
→ retrieval
→ chunks/documents/nodes
→ prompt
→ LLM
```

Evaluate inserting:

```text
retrieval
→ JEV evidence classification
→ filtered/annotated evidence
→ generation
```

Possible questions:

```text
Is this passage relevant?
Is this usable evidence?
Does it contradict another source?
Is it merely background?
Does it contain an instruction or prompt injection?
Is provenance adequate?
Is the evidence current enough?
```

Support:

- vector RAG,
- hybrid RAG,
- GraphRAG,
- knowledge graphs,
- document retrieval,
- web retrieval.

---

## Pattern E — After tool/action execution

Detect simplistic success checks such as:

```text
exit_code == 0
HTTP 200
function returned
no exception
```

Distinguish:

```text
operation succeeded technically
```

from:

```text
objective was accomplished semantically
```

Recommend JEV verification when appropriate.

Possible outcomes:

```text
succeeded
partially_succeeded
failed
state_changed_unexpectedly
new_blocker
verification_required
uncertain
```

---

## Pattern F — Central agent-loop transition

Detect loops similar to:

```text
observe
think
act
repeat
```

Evaluate JEV for:

```text
objective_complete?
blocked?
need_more_information?
need_replan?
need_human?
next_action_type?
```

Architecture:

```text
S_t
 ↓
JEV
 ↓
A_t
 ↓
environment
 ↓
S_t+1
```

JEV should be evaluated as a state-transition classifier, not as a replacement for the full reasoning model.

---

## Pattern G — Planner → executor boundary

Detect architectures where one model produces plans which are executed with little independent validation.

Candidate questions:

```text
Does the plan satisfy the requested objective?
Are dependencies unresolved?
Does an early step invalidate a later step?
Does this require approval?
Is a step unnecessary?
Does the plan violate a constraint?
Is sufficient evidence available to execute?
```

---

## Pattern H — Context and compaction

Detect:

```text
context truncation
summarization
memory pruning
conversation compaction
token-threshold behavior
```

Evaluate JEV for:

```text
keep
compress
drop
```

Questions:

```text
Is this still relevant?
Does it contain an unresolved constraint?
Would losing it materially affect future decisions?
Does it describe a failed approach that should not be repeated?
Has it been superseded?
Does it contain durable user preference or system state?
```

JEV should normally decide **what** to retain, not perform the generative summarization itself.

---

## Pattern I — Retry and recovery logic

Detect:

```text
try → fail → retry
```

and especially repeated model calls after failure.

Potential JEV choices:

```text
retry_same
retry_with_new_parameters
inspect_state
change_tool
replan
rollback
escalate
abort
wait
```

Identify loops where agents repeatedly reproduce the same failure.

---

## Pattern J — Multi-agent routing

Detect:

```text
task
→ orchestrator
→ specialist
```

Evaluate JEV for selection among:

```text
coding_agent
research_agent
tester
security_agent
reviewer
data_agent
human
```

Also evaluate:

```text
failure → specialist
review finding → specialist
subtask → specialist
```

---

## Pattern K — Code-review gates

Detect locations where:

```text
diff
tests
static analysis
review results
```

are converted into decisions.

Prefer decomposed questions:

```text
Does the diff satisfy the issue?
Are tests sufficient for the changed behavior?
Did the change exceed scope?
Is a failing test related to the patch?
Does the change introduce a security-sensitive action?
Does the change require more review?
```

Avoid vague questions such as:

```text
Is this code good?
```

---

## Pattern L — Graph and entity mutation

Detect:

```text
CREATE
MERGE
LINK
sameAs
DELETE RELATION
UPDATE NODE
entity resolution
deduplication
graph synthesis
```

Evaluate JEV for:

```text
different
related
same
uncertain
review
```

especially immediately before irreversible graph mutations.

---

## Pattern M — Final-answer validation

Detect answer-generation boundaries.

Potential questions:

```text
Does the response answer the request?
Does it contradict evidence?
Is a claim unsupported?
Was a required section omitted?
Did it violate an output constraint?
Are citations actually supporting the claims?
```

JEV evaluates the generated result; another model or deterministic code can perform revision.

# 4. Detect where JEV should NOT be used

This is mandatory.

The skill must actively identify anti-patterns.

Do not recommend JEV where deterministic computation is clearly better.

Examples:

```text
arithmetic
sorting
hash validation
exact comparisons
regex
parsing
JSON validation
schema validation
file existence
type checking
permissions
exact dates
database joins
deterministic state checks
known finite lookup tables
cryptographic checks
exit-code inspection
numerical thresholds
syntax validation
```

Create a specific field:

```text
deterministic_alternative
```

Values:

```text
none
weak
equivalent
preferred
mandatory
```

If deterministic logic is `preferred` or `mandatory`, strongly penalize or reject the candidate JEV placement.

---

# 5. Do not use JEV as a generative model where unnecessary

Identify attempts to use JEV for:

```text
writing code
writing essays
generating SQL
generating shell commands
writing long plans
summarization
creative generation
open-ended reasoning
```

Where appropriate, recommend:

```text
generative model
      ↓
JEV evaluator / classifier / selector
      ↓
deterministic execution
```

rather than forcing generation through JEV.

---

# 6. Decompose broad judgments into atomic questions

One of the skill's major responsibilities is designing good JEV questions.

Avoid:

```text
Is this good?
Is this correct?
Should we do it?
Is this safe?
```

Prefer decomposed questions such as:

```text
Does this satisfy requirement X?
Is dependency Y resolved?
Does evidence Z support this claim?
Would execution mutate production state?
Is user approval required?
Is there an unresolved blocker?
Is the proposed tool capable of the requested operation?
Did the previous operation accomplish the intended subgoal?
```

Each proposed JEV integration must include:

```yaml
jev_questions:
  - question:
    answer_type:
    allowed_answers:
    purpose:
    evidence_inputs:
    confidence_usage:
```

---

# 7. Model explicit bounded choices

Where possible, convert free-form decisions into finite choices.

Example:

```yaml
decision: recovery_strategy
choices:
  - retry_same
  - retry_modified
  - inspect
  - alternate_tool
  - replan
  - escalate
  - abort
```

The skill should recommend bounded `Choice`-style structures where this is appropriate.

---

# 8. Confidence must affect behavior

For every JEV integration, define how confidence is used.

Example:

```text
high confidence
    → execute bounded action

medium confidence
    → gather evidence / run additional check

low confidence
    → fallback model / deterministic inspection / human review
```

Support configurable thresholds.

Example:

```yaml
confidence_policy:
  execute: ">= 0.90"
  inspect_more: "0.65-0.90"
  escalate: "< 0.65"
```

Do not invent one universal threshold.

The correct threshold should depend on:

```text
risk
reversibility
cost
latency
impact
availability of verification
```

---

# 9. Separate assessment from policy

The generated integrations should usually follow:

```text
JEV produces:
    classification
    probability/confidence
    structured observations

Application code decides:
    execute
    block
    retry
    escalate
    require approval
```

For example:

```python
assessment = evaluate_action(...)

if deterministic_hard_block:
    block()

elif assessment.risk_probability >= HIGH_RISK_THRESHOLD:
    require_approval()

elif assessment.confidence < MINIMUM_CONFIDENCE:
    inspect_more()

else:
    execute()
```

Do not embed business/security policy invisibly inside prompts when deterministic application code can express it clearly.

---

# 10. Analyze downstream leverage

A candidate location should score higher when one wrong choice can create many downstream failures.

Model something like:

```text
decision error
→ wrong tool
→ wrong state
→ additional reasoning
→ additional tool calls
→ cascading failure
```

Estimate:

```text
fan_out
dependency_depth
expected_recovery_cost
state_corruption_risk
```

Use these to identify high-causal-leverage insertion points.

---

# 11. Recognize long-horizon reliability

The skill must understand that a small per-step reliability improvement can create a large end-to-end improvement.

For a workflow with:

```text
n dependent steps
per-step success probability p
```

estimate:

```text
P(successful workflow) ≈ p^n
```

Use this when assessing JEV in:

- autonomous agents,
- game-playing agents,
- coding agents,
- multi-step workflows,
- robotic/control systems.

Do not use independence assumptions silently.

Label this estimate as approximate unless independence is supported.

# 14. Detect interaction between multiple JEV placements

Do not evaluate insertion points only independently.

For example:

```text
JEV tool selection
+
JEV post-action verification
```

may work much better together.

Model combinations such as:

```text
router + verifier
retrieval filter + citation checker
planner validator + action gate
context selector + retry controller
entity classifier + graph mutation gate
```

Identify:

```text
complementary placements
redundant placements
conflicting placements
cascading latency
duplicated semantic decisions
```

Avoid stacking JEV unnecessarily.

# 15. Build an optimal-placement optimizer

Given many candidate placements, determine a practical integration set.

This should act like a constrained optimization problem.

Maximize:

```text
expected_quality_gain
+ expected_reliability_gain
+ expected_failure_reduction
+ expected_model_call_reduction
```

while minimizing:

```text
latency
cost
complexity
maintenance
false positives
false negatives
```

Subject to constraints such as:

```text
latency_budget
cost_budget
maximum_jev_calls_per_task
risk tolerance
required throughput
```

Output:

```text
recommended_minimal_set
recommended_balanced_set
recommended_maximum_reliability_set
```

Do not automatically recommend the largest number of JEV calls.

# 17. Measure rescues and regressions

For binary outcomes classify:

```text
Baseline Pass / JEV Pass
Baseline Fail / JEV Fail
Baseline Fail / JEV Pass   ← rescue
Baseline Pass / JEV Fail   ← regression
```

Calculate:

```text
rescue_count
regression_count

rescue_regression_ratio =
    rescues / regressions
```

Use McNemar-style paired analysis where appropriate.

---

# 18. Measure effect sizes and uncertainty

The skill should recommend/report:

```text
absolute improvement
relative improvement
effect size
confidence intervals
bootstrap confidence intervals
```

Example:

```text
task success:
baseline = 71.2%
JEV      = 79.5%

absolute Δ = +8.3 percentage points
```

Do not treat point estimates as sufficient evidence.

---

# 19. Support Bayesian usefulness analysis

Where useful, estimate:

```text
P(JEV > baseline | data)
```

More importantly:

```text
P(JEV improvement > minimum_useful_effect | data)
```

Example:

```text
P(Δ > 0) = 0.98
P(Δ > 0.02) = 0.81
```

Distinguish:

```text
probably better
```

from:

```text
probably useful enough to justify integration
```

---

# 20. Use multi-objective / Pareto analysis

Do not collapse everything into accuracy.

Track vectors such as:

```text
quality
cost
latency
tokens
reliability
safety
throughput
model_calls
```

Identify when JEV:

```text
Pareto dominates baseline
```

or when there is a tradeoff.

Examples:

```text
higher quality + lower cost = strong dominance

higher quality + much higher latency = tradeoff
```

Generate Pareto comparisons when multiple configurations exist.

---

# 21. Economic break-even analysis

Support calculations such as:

```text
added JEV inference cost
vs
reduction in failure probability
× cost per failure
```

Estimate:

```text
expected_savings
net_value
break_even_volume
```

Example:

```text
JEV added cost = $0.006/run
failure reduction = 4%
average failure cost = $0.40

expected savings:
0.04 × $0.40 = $0.016

net:
$0.016 - $0.006 = $0.010/run
```


# 27. Support offline replay

Whenever possible, capture enough information to replay decisions offline.

For example:

```yaml
decision_event:
  timestamp:
  source_location:
  state:
  evidence:
  candidate_actions:
  baseline_decision:
  baseline_result:
```

Then run JEV offline against the same decision state.

This allows:

```text
baseline vs JEV
```

without initially changing production behavior.

# 33. Implementation mode requirements

When explicitly authorized to modify code:

1. Create a branch/worktree where appropriate.
2. Preserve existing behavior until the experiment requires otherwise.
3. Add JEV integration behind a feature flag.
4. Add shadow mode if practical.
5. Instrument decisions.
6. Add structured logs.
7. Add tests.
8. Add configuration.
9. Add fallback paths.
10. Run existing test suites.
11. Add paired evaluation fixtures.
12. Benchmark latency and cost.
13. Document the integration.
14. Produce a diff summary.
15. Do not silently weaken security or validation logic.

# 34. Safety and reversibility

Every implementation should answer:

```text
What happens if JEV is unavailable?
What happens if JEV times out?
What happens if JEV returns low confidence?
What happens if JEV produces an invalid answer?
Can deterministic fallback continue operation?
Can this feature be disabled immediately?
```

Prefer:

```text
feature flags
timeouts
fallbacks
circuit breakers
shadow deployment
structured logging
```

# 35. Caching

Identify JEV decisions that can safely be cached.

Possible cache keys:

```text
normalized question
candidate choices
relevant state hash
evidence hash
model/version
policy version
```

Do not cache decisions where rapidly changing runtime state invalidates reuse.

Track:

```text
cache_hit_rate
latency_saved
cost_saved
stale_decision_rate
```

---

# 36. Calibration

When JEV returns probabilities/confidence, test calibration.

Support metrics such as:

```text
Brier score
Expected Calibration Error
reliability diagrams
```

A confidence of 0.90 should correspond approximately to 90% empirical correctness for comparable decisions if it is being interpreted probabilistically.

Do not assume confidence values are calibrated without testing.

---

# 37. Ablation testing

When multiple JEV placements are implemented, run ablations.

Example:

```text
A = no JEV
B = tool router only
C = verifier only
D = router + verifier
E = router + verifier + recovery
```

This identifies which placement creates the actual benefit.

---

# 38. Stop criteria

The skill must support concluding:

```text
JEV does not provide sufficient value here.
```

That is a valid outcome.

Recommend removal or non-adoption if:

```text
deterministic logic performs equally or better
latency exceeds value
cost exceeds value
regressions outweigh rescues
confidence is poorly calibrated
failure rate increases
behavior becomes less predictable
maintenance burden exceeds benefit
```

The skill exists to find **optimal use**, not maximize JEV usage.

# 44. JEV architectural philosophy

The skill should encode these defaults:

```text
LLMs generate.
JEV classifies/selects/evaluates.
Deterministic code enforces.
Instrumentation measures.
Experiments decide whether JEV stays.
```

This is a default architecture, not an absolute rule.

The skill is successful when it can take an unfamiliar repository and answer, with evidence:

> Where are the highest-leverage locations for JEV?

> Which decisions should remain deterministic?

> What questions and choices should be used?

> How should confidence affect execution?

> What fallback should exist?

> How much latency/cost will this add?

> How will we determine whether JEV actually helped?

> Which integrations should be implemented first?

The final result should transform JEV integration from intuition into a repeatable discipline of:
