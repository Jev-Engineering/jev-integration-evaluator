# JavaScript and TypeScript backend qualification plan

This document records the bounded implementation contract for issue #14.
The executable `js-*` commands support recipe C on a POSIX filesystem with
trusted Node and pinned TypeScript 5.8.3 tooling outside the target. The
synthetic support evidence is in `validation/JAVASCRIPT-TYPESCRIPT-SUPPORT.md`.

## First source shapes

| Host module | Selected seam | Required checks |
| --- | --- | --- |
| ESM JavaScript | One exported top-level `async` function with one `return await existing(request)` tail call | Static import/export names, unique binding, source hash, and actual entrypoint execution |
| CommonJS JavaScript | One top-level `async` function assigned once to `module.exports` or an exact named export | Export identity, unique binding, source hash, and actual entrypoint execution |
| TypeScript | The ESM async shape with an explicitly declared request/result type that the trusted compiler can transpile without a target configuration | Syntax diagnostics, controlled emit, source hash, and actual emitted entrypoint execution |

The first implementation must reject dynamic imports, decorators, nested selected
functions, branches inside the selected seam, multiple call sites, reassignment,
getter exports, top-level side effects that alter the selected binding, and
unsupported compiler syntax before a target write. Support for one shape cannot
be inferred from analysis-only discovery of another shape.

## Tool and runtime boundary

The trusted TypeScript 5.8.3 compiler under this package's tooling directory
parses and emits from supplied source text only. It must never read a target
`tsconfig`, load a target plugin, resolve target packages for transformation, or
execute target source while planning. The plan binds the compiler version,
parser/transformer bytes, original source, exact generated bytes, and all owned
files. The target's own module loader and entrypoint are used only by an
externally authorized verification schedule.

The backend uses a native JavaScript runtime shipped as owned, hashed
source beside the generated adapter. It does not spawn Python or import target
packages during planning. A host explicitly creates one runtime owner at
startup and gives every placement the same process-local budget and task ledger.
The implemented recipe is bounded registered tool routing (`C`); other
A–M recipes remain unsupported until their distinct contracts are qualified.
Finite action IDs, stable task identity, exact source/spec/receipt binding,
explicit host gates, fixed fallback and timeout behavior, audit before effects,
and an exactly-once effect ledger are required before the `C` path can be
called supported. A synthetic pass is neither provider connectivity nor
observed benefit or activation authority.

## Qualification sequence

1. Independently hash and review source, export, callback, policy and effect sites.
2. Produce a private, complete patch and runtime plan; validate parser output and
   regenerate the exact bytes from archived preimages on load.
3. Execute authorized baseline entrypoints in each module format, independently
   record effects and policy outcomes, and retain receipt anchors.
4. Apply only the reviewed owned bytes, execute off/shadow/authorized active
   schedules through edited entrypoints, and reject missing outcomes.
5. Test cancellation, rejection, argument/effect ordering, shared-budget
   contention, receipt tampering, source drift, import collision, rollback, and
   installed-package behavior on the actually supported platform.

The support matrix must list implemented A-M recipes individually; all other
recipes and module shapes remain explicit unsupported results.

## Owned bundle commands

`js-support` returns the versioned static A–M support matrix and explicitly
separates the older repository discovery contract from this backend. It does
not inspect or verify a target.

`js-plan --repo ROOT --spec REVIEWED.json --bundle NEW_PRIVATE_DIRECTORY
--tooling TRUSTED_TOOLING` reads the reviewed flat source without importing it,
uses the pinned compiler outside the target, and archives private source
preimages, exact generated bytes, tool hashes and a sealed patch. The
specification names one `javascript.C` candidate, an exact source hash,
existing finite host binding symbols, a default-off native runtime contract,
and the SHA256 of externally retained verification cases. The owned files are
the host source, `jev_adapter.cjs`, `jev_runtime.cjs`, and for TypeScript the
emitted `host.mjs`. Every load regenerates the transform from the archived
preimage and compares exact hashes before target mutation or execution.

`js-verify --phase baseline --approve-execution --cases CASES.json` executes
the host's public entrypoint in the trusted-host environment. For TypeScript,
the pinned compiler emits the pre-edit source in a temporary directory without
loading a target compiler configuration. The returned receipt SHA256 must be
retained outside the bundle. `js-apply --approve BUNDLE_SHA256
--baseline-sha256 RECEIPT_SHA256` checks the complete owned baseline and exact
receipt before applying. `js-verify --phase modified` executes the edited
entrypoint; `js-status --trusted-modified-sha256 RECEIPT_SHA256` can then
report externally anchored verification. Interrupted operations require
`js-recover` with exact receipt evidence, or `js-rollback` with the separate
rollback digest. Rollback restores only matching owned bytes and refuses
concurrent edits. The commands do not install dependencies, grant egress or
activate a provider.

Verification cases are supplied separately to avoid archiving request text;
their exact digest is fixed in the reviewed specification. Receipts retain
case counts and observation digests, not raw request/output payloads. The
synthetic host fixture calls a probe-owned effect sensor, so the edited
entrypoint is checked against an observation separate from its exported
`events` array. Other hosts need an independently reviewed effect observation
site before their outcomes can be qualified. The
private bundle contains source preimages required for exact rollback and must
remain owner private and outside the target. The trusted-host verifier is not
an isolation boundary for hostile target code.
