# JavaScript and TypeScript backend qualification plan

This document records the initial bounded implementation matrix for issue #14.
It is a design input, not a claim that the executable backend is available.

## First source shapes

| Host module | Selected seam | Required checks |
| --- | --- | --- |
| ESM JavaScript | One exported top-level function with one `return existing(request)` tail call | Static import/export names, unique binding, source hash, and actual entrypoint execution |
| CommonJS JavaScript | One top-level function assigned once to `module.exports` or an exact named export | Export identity, unique binding, source hash, and actual entrypoint execution |
| TypeScript | The ESM shape with an explicitly declared request/result type that the trusted compiler can transpile without a target configuration | Syntax diagnostics, controlled emit, source hash, and actual emitted entrypoint execution |

The first implementation must reject dynamic imports, decorators, nested selected
functions, branches inside the selected seam, multiple call sites, reassignment,
getter exports, top-level side effects that alter the selected binding, and
unsupported compiler syntax before a target write. Support for one shape cannot
be inferred from analysis-only discovery of another shape.

## Tool and runtime boundary

The trusted TypeScript 5.8.3 compiler under this package's tooling directory
parses and emits from supplied source text only. It must never read a target
`tsconfig`, load a target plugin, resolve target packages for transformation, or
execute target source while planning. The plan binds the compiler version,
parser/transformer bytes, original source, exact generated bytes, and all owned
files. The target's own module loader and entrypoint are used only by an
externally authorized verification schedule.

The runtime strategy must be chosen before implementation. A native JavaScript
runtime needs finite action IDs, a shared process-local budget owner, stable task
identity, source/spec/receipt binding, explicit host gates, fixed fallback and
timeout behavior, audit before effects, and an exactly-once effect ledger. An
installed Python bridge instead needs a persistent, authenticated protocol with
the same properties and explicit transport-failure behavior. Neither strategy
may use a synthetic pass as provider connectivity, observed benefit, or
activation authority.

## Qualification sequence

1. Independently hash and review source, export, callback, policy and effect sites.
2. Produce a private, complete patch and runtime plan; validate parser output and
   regenerate the exact bytes from archived preimages on load.
3. Execute authorized baseline entrypoints in each module format, independently
   record effects and policy outcomes, and retain receipt anchors.
4. Apply only the reviewed owned bytes, execute off/shadow/authorized active
   schedules through edited entrypoints, and reject missing outcomes.
5. Test cancellation, rejection, argument/effect ordering, shared-budget
   contention, receipt tampering, source drift, import collision, rollback, and
   installed-package behavior on the actually supported platform.

The support matrix must list implemented A-M recipes individually; all other
recipes and module shapes remain explicit unsupported results.
