# Finite separately installed package owner v1

The `registered-alpha-queue-pair-v1` profile composes exactly two independently
installed Python distributions: the reviewed registered Alpha host and the
reviewed work queue. It requires distinct package, environment and candidate
identities. A third, genuinely built and independently installed owner
application runs its normal `registered-packages` console command. This is a
Linux x86-64 CPython 3.13 offline software profile. Its test endpoint and issuer
are synthetic local TLS fixtures. It does not qualify a real Jev provider,
canary, active treatment, combined benefit, or production deployment.

`derive_installed_packages_binding` is a read-only provenance primitive. Supply the
complete package/install plans and receipts for both members, their externally
retained receipt hashes, and one explicit private common source root. It
rechecks installed RECORD snapshots before launching metadata inspection;
extra executable files, changed initializers and duplicate origins fail closed.
This primitive cannot start a connected runtime because it has no owner.

`plan_packages_owner`, `apply_packages_owner`, `packages_owner_source_status`
and `rollback_packages_owner` operate on a freshly authored owner source tree.
The finite parser accepts one literal canonical task and distinct Alpha/queue
input dictionaries, an exact trusted helper import, and a two-statement main.
It accepts exactly those two function definitions and rejects helper, main and
request-factory shadowing, extra functions, module import hooks and dunder import
bindings. Normal from-import can invoke a module hook before main; a signed
source preimage does not relax this finite grammar. Applying requires the
exact plan approval and an external private transaction directory. Rollback
restores the exact source preimage and leaves installed environments and runtime
history intact. None of these operations imports a member or starts a console.

`plan_owner_package`, `build_owner_package`, `plan_owner_install`,
`install_owner_package` and `owner_installation_status` issue genuine
owner-specific contracts and receipts. The owner project has a finite declared
setuptools configuration, the fixed console command, a pinned evaluator
requirement and an explicitly prepared offline wheelhouse. Its receipts are
never fabricated from member receipts. `derive_owned_packages_binding` binds
that owner command, module, evaluator, dependencies and both member executable
closures under the common root. Signed scope includes exact bytes and origins.
The finite closure is bounded to 4096 files, 4 MB per file and 64 MB total.
Legacy runtime file-count and size limits remain unchanged.

The existing connected delivery API accepts this profile with separately
signed installed-binding and egress authorities, an exact public verifier key,
one durable ledger and an expiring launch scope. Its generated helper selects
both exact adapters, pins the original complete request and canonical task,
and wires their existing runtime seams to one `HostRuntimeLifecycle`. A finite
captured-source loader verifies source before imports and ignores member
bytecode and import-path shadows. Failed imports remove the loader and partial
member modules. Both members consume one per-task and total request budget. Only this signed
finite owner shadow profile permits their distinct original canary scope IDs;
each router still must match its own exact signed SPEC scope. Aggregate canary
and active modes refuse before dispatch. Older profiles retain their shared
scope equality rule.
Stopping a command never restores spending or erases closed-task tombstones.

Shadow assessment preserves the original application actions. Those baseline
calls do not run the treatment `Context.host_operation` journal. The owner
therefore journals each normal public entrypoint invocation separately, with
its exact candidate, original input digest and `owner:public_entry` or
`owner:handle_job` identity. It claims before calling the source-owned entry,
completes only after a successful stable invocation, and retains uncertainty
on failure. These are entrypoint claims, not treatment registry claims or
claims of an observed treatment benefit. Normal command completion closes the
canonical task durably; later invocation checks both placements before effects.

The required installed fixture is `tests/test_connected_packages_installed.py`.
It builds all three applications, launches the normal owner command through
public delivery APIs, checks independent raw effects and both actual entrypoint
claims, and tests restart refusal with unused global admission headroom. A
fresh, separately signed one-call per-task fixture tests common budget
exhaustion. A source rollback leaves the durable ledger unchanged. These
checks must pass on the immutable source before qualification is reported;
parser doubles and primitive binder tests alone are not installed evidence.

The authored owner qualification fixture declares a ten-second assessment
deadline in each fresh member compile request before scanning and source
review, and checks the actual installed specifications. Full provenance
rechecks remain inside that deadline. This proves the mechanics under the
declared offline fixture budget; it does not establish performance at the
unchanged two-second default or a real-provider latency result. Request and
spending caps, late-response refusal, and legacy fixture defaults are unchanged.
